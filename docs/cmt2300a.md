# CMT2300A-Treiber (Tuya SH4): 433-MHz-Empfang und -Senden

Mit diesem Treiber arbeitet ein Tuya-Modul **SH4** (BK7231N + Sub-GHz-Funkchip **CMT2300A**) unter OpenBeken als **433-MHz-Bridge**:

- **Empfang:** Funk-Wettersensoren, Funksteckdosen, Rollläden, X10, Klingeln und andere Fernbedienungen (OOK/ASK). Die Werte gehen als JSON per MQTT raus und stehen auf der Hauptseite.
- **Senden:** beliebige Fernbedienungscodes (z. B. Türklingel), Intertechno/KlikAanKlikUit und **virtuelle Funksensoren**. Damit lassen sich Werte aus Home Assistant oder openHAB an eine Funk-Wetterstation schicken.
- **Diagnose:** Frequenzsuche, Spektrum-Anzeige, Protokoll-Spy und Laufzeitzähler.

## 1. Inbetriebnahme

### Firmware

Eingeschaltet wird der Treiber zur Compile-Zeit in `src/obk_config.h` im Block `#elif PLATFORM_BEKEN`:

```c
#define ENABLE_DRIVER_SH4 1
```

Die Pins des CMT2300A sind im Treiber fest eingetragen und werden **nicht** über die OBK-Pin-Rollen eingestellt:

| Signal | Pin |
| --- | --- |
| SCLK | P14 |
| SDIO | P16 |
| CSB | P6 |
| FCSB | P26 |
| GPIO1 / DCLK | P20 |
| GPIO2 / DOUT–DIN | P22 |

Die übrigen Pins des SH4 werden normal per Pin-Rolle eingestellt: `P7 = IRSend`, `P8 = IRRecv`, `P9 = WifiLED`, `P23 = Btn`.

### Starten (autoexec.bat)

```text
startDriver CMT2300A
startDriver IR
```

Danach erscheint auf der Hauptseite der Abschnitt **„CMT2300A Funk-Empfang“** mit den letzten 8 Telegrammen.

### OTA-Update

Während eines OTA-Updates **pausiert der Treiber selbst**. Er hält den Abtast-Timer an und leert seine Warteschlangen, im Log steht dann `CMT: OTA laeuft - Empfang/Senden pausiert`. Scheitert das OTA, läuft der Empfang danach von allein weiter.

> Firmware-Stände vor diesem Mechanismus (bis Build 06.11.2026 18:59) brauchen vor dem OTA ein `stopDriver CMT2300A`, sonst scheitert das Update.

### Schutz vor Neustartschleifen

Ist der vorherige Start gescheitert (OBK „incomplete boots“ ≥ 2), startet die Protokoll-Engine **ausgeschaltet**. Das zeigt `cmtproto`, alle Protokolle stehen dann auf „AUS“. Wieder einschalten:

```text
cmtproto all on
```

## 2. Befehlsübersicht

Alle Befehle funktionieren in der Web-Konsole, in `autoexec.bat`, über HTTP (`http://<ip>/cm?cmnd=<befehl>`) und über MQTT (Topic `cmnd/<topic>/<befehl>`, Payload = Argumente). Die Ausgaben erscheinen im Log.

| Befehl | Zweck |
| --- | --- |
| `cmtinfo` | Status: Chip, Frequenz, RX/TX-Zähler, RSSI, virtuelle Sensoren |
| `cmtproto [<Name\|Nr\|all> on\|off]` | Empfangsprotokolle mit Zählern auflisten / ein- und ausschalten |
| `cmtproto voll on\|off` | gekürzte Pakete (Rauschen ohne Pause davor) auswerten (Standard) oder überspringen |
| `cmtproto reset` | Zähler und Zeitmessung zurücksetzen |
| `cmtsend …` | Fernbedienungscode senden (z. B. Klingel), siehe [4.1](#41-fernbedienungscodes-cmtsend) |
| `cmtsendp <Protokoll> <Hex> [Bits] [Wdh]` | Rohdaten mit dem Timing eines Protokolls senden |
| `cmtkaku <Id> <Einheit> <on\|off\|0..15> [Gruppe]` | Intertechno / KlikAanKlikUit / Nexa schalten |
| `cmtsensor …` | virtuellen Funksensor anlegen und senden, siehe [4.4](#44-virtuelle-funksensoren-cmtsensor) |
| `cmtflex …` | eigenes Protokoll zur Laufzeit definieren, siehe [3.4](#34-eigene-protokolle-cmtflex) |
| `cmtfreq [MHz]` | Frequenz anzeigen / setzen |
| `cmtvco [min max]` | VCO-Bereich anzeigen / setzen (Standard 1680–2040 MHz) |
| `cmtscan [von bis [kHz [s]]]` | Frequenz eines Senders suchen (RSSI-Sweep, dabei Sender drücken) |
| `cmtspy [MHz [s]]` | Protokoll-Spy: nächsten Burst aufzeichnen und analysieren |
| `cmtspec [von bis [kHz [MQTT_s [schnell]]]]` | Spektrum dauernd messen (Anzeige auf der Hauptseite + MQTT) |
| `cmtspec off \| reset \| clear` | Spektrum anhalten / Max-Hold löschen / Speicher freigeben |
| `cmtcap [ms] [clk]` | DOUT roh aufzeichnen und dekodieren (**blockiert**, Standard 1500 ms) |
| `cmtstop` | Scan / Spy / Spektrum abbrechen |
| `cmtcarrier [ms]` | Testträger senden (max. 3000 ms) |
| `cmtreg <a> [<v>]` | Register lesen / schreiben (hex) |
| `cmtdump` | alle Register 0x00–0x6F ausgeben |

### 3.2 Sensor-Meldungen (Wetterstationen)

Jedes erkannte Sensor-Telegramm wird gemeldet als:

```json
{"RfSensor":{"Protocol":"Nexus","Id":"3D","Channel":1,"Battery":1,"Temperature":23.1,"Humidity":38}}
```

Gesendet wird es an mehrere Topics, damit sich Sensoren je nach Hausautomation einfach abgreifen lassen:

| Topic | Inhalt |
| --- | --- |
| `<topic>/RfSensor` | JSON jedes Sensors |
| `<topic>/RfSensorCh<N>` | JSON, nur Sensoren auf Kanal N (`RfSensorCh1` …) |
| `<topic>/RfSensorProtocol` | Protokollname (`Nexus`) |
| `<topic>/RfSensor<Feld>` | Einzelwert, z. B. `RfSensorTemperature` = `23.1` |

Jedes Topic wird zweimal gesendet, **mit und ohne** `/get` am Ende (z. B. `…/RfSensor` und `…/RfSensor/get`).

> **Wichtig:** Ein Topic wie `RfSensorTemperature` oder `RfSensorCh1` empfängt **alle** Sensoren, die auf diese Beschreibung passen, auch die der Nachbarn. Für einen bestimmten Sensor deshalb immer das JSON nehmen und nach `Id` und `Protocol` filtern, siehe Beispiele in [7](#7-home-assistant) und [8](#8-openhab). Die `Id` vieler Sensoren ändert sich beim Batteriewechsel.

**Felder:**

| Feld | Bedeutung |
| --- | --- |
| `Protocol` | Name des Decoders (siehe Tabelle 3.1) |
| `Id` | Geräte-ID (hex) |
| `Channel` | Kanalschalter am Sensor |
| `Battery` | `1` = in Ordnung, `0` = schwach |
| `Temperature` | °C, eine Nachkommastelle |
| `Humidity` | % rel. Feuchte |
| `Moisture` | Bodenfeuchte (Springfield) |
| `Button` | Testtaste gedrückt (`1`) |
| `WindAvg`, `WindGust`, `WindDir`, `Rain` | Wind/Regen (WH1080) |
| `Model` | Modellcode (Oregon) |

### 3.3 Fernbedienungen, Schalter, Rollläden

Protokolle ohne Messwerte gehen nach `<topic>/RfProtocol`:

```json
{"RfProtocol":{"Protocol":"NewKaku","Id":"1A2B3C4","Unit":1,"Group":0,"Cmd":"On"}}
{"RfProtocol":{"Protocol":"X10","House":"A","Unit":3,"Cmd":"Off"}}
{"RfProtocol":{"Protocol":"Somfy","Cmd":"Up","Counter":1234,"Id":"0A1B2C","Key":5}}
{"RfProtocol":{"Protocol":"RcSwitch1","Data":"5551","Bits":16,"Tristate":"FF0F0F"}}
```

**24-Bit-Codes** (die meisten Funksteckdosen, Klingeln und Fernbedienungen nach PT2262/EV1527) meldet zusätzlich der klassische Decoder im Format einer RF-Bridge:

```text
<topic>/RfReceived/get  →  {"RfReceived":{"Sync":8970,"Low":300,"High":850,"Data":"6B59A2"}}
<topic>/RfCode/get      →  6B59A2
```

Ein Ereignis ohne Wert lässt sich am einfachsten auf `RfCode` auslösen, z. B. ein Tastendruck oder die Klingel.

### 3.4 Eigene Protokolle (`cmtflex`)

Für Geräte, die keiner der Decoder kennt, lässt sich zur Laufzeit ein eigenes Protokoll anlegen. Es gilt bis zum Neustart, für Dauerbetrieb gehört es in `autoexec.bat`. Möglich sind bis zu 8 eigene Protokolle.

```text
cmtflex <Name> <PPM|PWM|PCM|DMC|RCS> <kurz_us> <lang_us> <gap_us> <reset_us> [BitsMin[-BitsMax]] [Wdh] [sync_us] [Puls_us]
cmtflex <Name> del
cmtflex list
```

| Modulation | Bedeutung |
| --- | --- |
| `PPM` | Pausenlänge kodiert das Bit (kurze Pause = 0) |
| `PWM` | Pulslänge kodiert das Bit (kurzer Puls = 1) |
| `PCM` | feste Bitzeit (z. B. Manchester) |
| `DMC` | Differential Manchester |
| `RCS` | rc-switch (Puls länger als Pause = 1) |

Treffer kommen als `{"RfProtocol":{"Protocol":"<Name>","Data":"…","Bits":…}}`. Die Zeiten liefert `cmtspy`, während man den Sender drückt.

Beispiel (Funktaster mit 400/1200 µs PWM, 24 Bit, mindestens 2 gleiche Wiederholungen):

```text
cmtflex Taster PWM 400 1200 2000 8000 24 2
```

## 4. Senden

### 4.1 Fernbedienungscodes (`cmtsend`)

Für Codes im RF-Bridge-Format (Sync-Puls, dann Bits aus kurzem und langem Puls):

```text
cmtsend <Data> [Wdh]
cmtsend <Data> <Sync_us> <Low_us> <High_us> [Wdh] [Bits]
cmtsend {"Sync":8970,"Low":300,"High":850,"Data":"6B59A2"}
```

- Ohne Zeiten nimmt `cmtsend` die Zeiten des zuletzt empfangenen gleichen Codes, sonst 8970/300/850.
- Das JSON-Format entspricht direkt der Empfangsmeldung `RfReceived` und kann zusätzlich `"Repeat"` und `"Bits"` enthalten.
- Für Sonderfälle wie manche Klingeln gibt es `"T0H"`, `"T0L"`, `"T1H"`, `"T1L"` (High/Pause für Bit 0/1) und `"Merged":1` (kein Sync-Puls, die Lücke ersetzt die letzte Pause).

**Beispiel Türklingel** (getestet):

```text
cmtsend DEE308 20000 450 1450 20
```

Das sind Code `DEE308`, Sync 20 ms, kurz 450 µs, lang 1450 µs und 20 Wiederholungen.

### 4.2 Rohdaten mit Protokoll-Timing (`cmtsendp`)

```text
cmtsendp <Protokoll> <Hex> [Bits] [Wdh]
cmtsendp RcSwitch2 5551 24 8
```

Das funktioniert mit jedem Protokoll aus `cmtproto`, auch mit eigenen `cmtflex`-Protokollen.

### 4.3 Intertechno / KlikAanKlikUit (`cmtkaku`)

```text
cmtkaku <Id_hex> <Einheit 1..16> <on|off|0..15> [Gruppe]
cmtkaku 1A2B3C 1 on
cmtkaku 1A2B3C 1 off
cmtkaku 1A2B3C 2 8          # Dimmer auf Stufe 8
cmtkaku 1A2B3C 1 off 1      # Gruppenbefehl: alle aus
```

Zum **Anlernen** die Steckdose in den Lernmodus versetzen (meist kurz nach dem Einstecken) und dann den `on`-Befehl senden. Die Id ist frei wählbar (26 Bit).

### 4.4 Virtuelle Funksensoren (`cmtsensor`)

Die Bridge kann sich als Funk-Thermometer ausgeben. Damit lassen sich z. B. Werte aus Home Assistant an eine vorhandene Funk-Wetterstation schicken. Es gibt 8 Speicherplätze (Slot 1–8) für virtuelle Sensoren. Jeder sendet sofort und danach von selbst im eingestellten Intervall.

```text
cmtsensor <Kanal> <Temp> [Feuchte] [Id] [Batterie] [Intervall_s] [Protokoll]
cmtsensor {"Channel":1,"Temperature":21.5,"Humidity":45,"Id":"5A","Battery":1,"Interval":60,"Protocol":"Nexus"}
cmtsensor {"Slot":5,"Channel":1,"Temperature":21.5,"Id":"65","Interval":60,"Protocol":"Acurite606"}
cmtsensor <Slot> <Protokoll>     # Protokoll eines Platzes wechseln (Werte und Kanal bleiben)
cmtsensor <Slot> off             # virtuellen Sensor abschalten
cmtsensor protocols              # sendefähige Protokolle mit Kanal- und Temperaturbereich
```

- `Intervall` = 0 sendet nur einmal.
- **Slot und Kanal:** Ohne `"Slot"` ist der Speicherplatz gleich dem Kanal (Kanal 2 landet in Slot 2). Mit `"Slot"` (nur im JSON) sind beide getrennt, und `Channel` ist nur der Kanal im Telegramm. So lassen sich mehrere Sensoren mit demselben Kanal betreiben, z. B. für zwei Stationen, die beide Kanal 1 bekommen. Fehlt bei `"Slot"` der `Channel`, behält ein belegter Platz seinen Kanal, ein neuer bekommt Kanal = Slot. `cmtinfo` zeigt Slot und Kanal.
- Der erlaubte Kanalbereich hängt vom Protokoll ab (z. B. Nexus 1–4, inFactory 1–3, F007TH 1–8). `cmtsensor protocols` zeigt ihn an.
- Standardprotokoll ist Nexus. Die meisten Wetterstationen von TFA, Technoline, Sencor und Hama verstehen es.

Beispiel: Außentemperatur aus Home Assistant jede Minute an Kanal 2 der Wetterstation:

```text
cmtsensor {"Channel":2,"Temperature":6.6,"Humidity":84,"Id":"5A","Interval":60,"Protocol":"Nexus"}
```

Die Werte lassen sich jederzeit mit demselben Befehl aktualisieren, das Intervall läuft dabei weiter.

Beispiel: zwei Stationen, beide mit der Außentemperatur auf Kanal 1. Die eine versteht Nexus, die andere Acurite606:

```text
cmtsensor {"Slot":1,"Channel":1,"Temperature":7.9,"Humidity":86,"Id":"51","Interval":60,"Protocol":"Nexus"}
cmtsensor {"Slot":5,"Channel":1,"Temperature":7.9,"Id":"65","Interval":60,"Protocol":"Acurite606"}
```

> Virtuelle Sensoren gelten nur bis zum Neustart der Bridge. Für den Dauerbetrieb sendet deshalb Home Assistant oder openHAB den `cmtsensor`-Befehl regelmäßig (siehe 7.5 und 8.3). Die Bridge sendet dazwischen selbst im eingestellten Intervall weiter.

#### Welches Protokoll versteht meine Station?

Ist der Original-Sensor verloren, lässt sich das passende Protokoll durch Ausprobieren finden:

1. Die Station in den Sensor-Suchmodus versetzen (meist Batterien kurz raus und wieder rein, oder die Such-/Sensortaste lange drücken) und den gewünschten Kanal wählen.
2. Alle sendefähigen Protokolle nacheinander auf diesem Kanal senden, **jedes mit einer anderen Temperatur**:

   ```text
   cmtsensor 1 11.1 50 A1 1 0 GT-WT-02
   cmtsensor 1 12.2 50 A1 1 0 Nexus
   cmtsensor 1 13.3 50 A1 1 0 Prologue
   cmtsensor 1 14.4 50 A1 1 0 Rubicson
   cmtsensor 1 15.5 50 A1 1 0 inFactory
   cmtsensor 1 16.6 50 A1 1 0 Springfield
   cmtsensor 1 17.7 50 A1 1 0 Acurite606
   cmtsensor 1 18.8 50 A1 1 0 Bresser3CH
   cmtsensor 1 19.9 50 A1 1 0 F007TH
   cmtsensor 1 21.0 50 A1 1 0 LaCrosseTX
   cmtsensor 1 22.1 50 A1 1 0 WH2
   ```

   Zwischen den Befehlen jeweils ~5 s warten.
3. Die angezeigte Temperatur verrät das Protokoll. Danach den Sensor dauerhaft einrichten und **die Id beibehalten**, denn die Station merkt sich beim Anlernen die ID.

Beispiel: Eine ca. 14 Jahre alte Lidl-Auriol-Station hat 17,7 °C angezeigt, versteht also **Acurite606** (nur Temperatur):

```text
cmtsensor 1 17.7 0 A1 1 30 Acurite606
```

## 5. Diagnose

### 5.1 `cmtinfo`

```text
CMT Frequenz RX=434202 kHz TX=433919 kHz
CMT RX an period=50us frames=13 reports=0 ringDrops=0 ...
CMT TX frei gesendet=41 Fehler=0 Warteschlange=0
CMT Protokolle: Pakete=1160 Meldungen=20 (Details: cmtproto)
CMT virt. Sensor Slot=2 Kanal=2 Nexus Id=5A Temp=6.6 Feuchte=84 ... Intervall=60 s, zuletzt vor 34 s
CMT RSSI_CODE=10 RSSI_DBM=13 GPIO1=0 GPIO2=0
```

`ringDrops` > 0 im Normalbetrieb bedeutet, dass die Auswertung nicht hinterherkommt. Während `cmtspy` und `cmtcap` ist das normal.

### 5.2 `cmtproto`: Zähler der Protokoll-Engine

Je Protokoll:

```text
CMT 1  Nexus  an  PPM 1000/2000 gap 3000 reset 5000  Nachr.=15 Meld.=4 ms=70/max 20 [TX cmtsensor] ...
```

- `Nachr.`: so oft lief der Decoder.
- `Meld.`: gültige Telegramme.
- `ms`/`max`: Rechenzeit gesamt bzw. für den längsten Durchlauf.

Summenzeile:

```text
CMT Pakete=27 (Fenster verschoben 512 x; gekuerzt 15, davon ausgewertet 15, Meld. daraus 11; Paare/Paket 421)
    zwischengelagert=2 verworfen(belegt)=0 verteilt=25 ms=3104 max=188 ms/Paket Meldungen=17
CMT MQTT: gesendet=880 verloren=0 wartend=0 Byte
```

| Zähler | Bedeutung |
| --- | --- |
| Fenster verschoben | Dauerrauschen ohne Pause, das Fenster ist weitergeglitten (kostet nichts) |
| gekürzt / Meld. daraus | Pakete mit Rauschen davor und die Telegramme, die darin gefunden wurden |
| zwischengelagert | kurze Pakete, die während einer Auswertung im Ersatzpuffer warteten |
| verworfen(belegt) | Pakete, die verloren gingen, weil noch ausgewertet wurde (sollte ≈ 0 sein) |
| verteilt | Auswertungen, die auf mehrere Ticks verteilt wurden (normal) |
| MQTT verloren | Werte, die nicht in die MQTT-Warteschlange passten |

### 5.3 Frequenz und Signal finden

```text
cmtscan 433.0 434.8 25 10     # 433,0–434,8 MHz in 25-kHz-Schritten, 10 s lang: Sender drücken
cmtspy                        # nächsten Burst aufzeichnen, Timing + Protokollvorschlag
cmtspec                       # Spektrum dauerhaft auf der Hauptseite (Empfang ruht!)
cmtspec off
```

`cmtspec` sendet das Spektrum zusätzlich als JSON nach `<topic>/RfSpectrum/get`.

### 5.4 Speicher und Last

Im Log steht jede Sekunde eine Zeile wie `Time 120, idle 52000/s, free 47328, …`.

- **`idle`** sollte im Ruhezustand bei mehreren 10 000/s liegen. Werte unter ~10 000 bedeuten Dauerlast, meist durch einen gestörten IR-Empfänger, siehe [9](#9-ir-infrarot-auf-dem-sh4).
- **`free`** (Heap) liegt im Ruhezustand bei ~47–49 KB. **OBK startet das Modul neu, wenn länger als 5 s weniger als 25 KB frei sind** (Neustart-Grund „Rbt“). Die OBK-Web-App braucht kurzzeitig bis zu 30 KB, deshalb sie nicht dauerhaft offen lassen.

## 6. MQTT-Referenz

### Vom Gerät gesendet

| Topic | Payload | Wann |
| --- | --- | --- |
| `<topic>/RfSensor` (+ `/get`) | JSON `{"RfSensor":{…}}` | jedes Sensor-Telegramm |
| `<topic>/RfSensorCh<N>` (+ `/get`) | JSON | Sensor mit Kanal N |
| `<topic>/RfSensorProtocol` (+ `/get`) | Protokollname | Sensor |
| `<topic>/RfSensor<Feld>` (+ `/get`) | Einzelwert | Sensor, je Feld |
| `<topic>/RfProtocol` (+ `/get`) | JSON `{"RfProtocol":{…}}` | Schalter, Fernbedienung, Rollladen, `cmtflex` |
| `<topic>/RfReceived/get` | JSON `{"RfReceived":{…}}` | 24-Bit-Code (RF-Bridge-Format) |
| `<topic>/RfCode/get` | Code als Hex | 24-Bit-Code |
| `<topic>/RfSpectrum/get` | JSON | `cmtspec` läuft |
| `<topic>/ir/get` | `IR_NEC 0x1 0x1A 0 (32 bits)` | IR empfangen (OBK-Flag 14) |

Gesendet wird über eine Warteschlange, ein Topic je ~5 ms Tick. Eine Sensor-Meldung mit allen Topics braucht deshalb ~1–2 s. Ohne MQTT-Verbindung wird nichts gepuffert.

### An das Gerät (Befehle)

Topic `cmnd/<topic>/<befehl>`, Payload = Argumente:

```text
cmnd/wlan2mqtt/irrfbridge1/cmtsend     DEE308 20000 450 1450 20
cmnd/wlan2mqtt/irrfbridge1/cmtkaku     1A2B3C 1 on
cmnd/wlan2mqtt/irrfbridge1/cmtsensor   {"Channel":2,"Temperature":6.6,"Humidity":84,"Id":"5A","Interval":60}
cmnd/wlan2mqtt/irrfbridge1/IRSend      NEC-1-1A-0
```

Test von der Kommandozeile (mosquitto):


## 7. Home Assistant

Der Treiber bringt keine MQTT-Discovery mit, die Entitäten werden in `configuration.yaml` angelegt (oder in einer eingebundenen `mqtt.yaml`).

### 7.1 Funk-Thermometer als Sensor

Ein bestimmter Sensor wird über `Protocol` und `Id` herausgefiltert. Die Bedingung `this.state` behält den alten Wert, wenn ein anderer Sensor auf demselben Kanal sendet:

```yaml
mqtt:
  sensor:
    - name: "Wohnzimmer Temperatur"
      unique_id: rf_nexus_3d_temp
      state_topic: "wlan2mqtt/irrfbridge1/RfSensorCh1"
      device_class: temperature
      state_class: measurement
      unit_of_measurement: "°C"
      value_template: >
        {% set s = value_json.RfSensor %}
        {% if s.Protocol == 'Nexus' and s.Id == '3D' %}{{ s.Temperature }}{% else %}{{ this.state }}{% endif %}
      expire_after: 600            # nach 10 min ohne Telegramm "nicht verfügbar"

    - name: "Wohnzimmer Feuchte"
      unique_id: rf_nexus_3d_hum
      state_topic: "wlan2mqtt/irrfbridge1/RfSensorCh1"
      device_class: humidity
      state_class: measurement
      unit_of_measurement: "%"
      value_template: >
        {% set s = value_json.RfSensor %}
        {% if s.Protocol == 'Nexus' and s.Id == '3D' %}{{ s.Humidity }}{% else %}{{ this.state }}{% endif %}
      expire_after: 600

  binary_sensor:
    - name: "Wohnzimmer Sensor Batterie"
      unique_id: rf_nexus_3d_bat
      state_topic: "wlan2mqtt/irrfbridge1/RfSensorCh1"
      device_class: battery          # an = Batterie schwach
      value_template: >
        {% set s = value_json.RfSensor %}
        {% if s.Id == '3D' %}{{ 'ON' if s.Battery == 0 else 'OFF' }}{% else %}{{ this.state | upper }}{% endif %}
```

**Tipp:** Unbekannte Sensoren in der Nachbarschaft findet man, indem man `wlan2mqtt/irrfbridge1/RfSensor` eine Weile mitliest (*Einstellungen → Geräte & Dienste → MQTT → Konfigurieren → Topic abonnieren*).

### 7.5 Werte an eine Funk-Wetterstation senden (virtueller Sensor)

```yaml
automation:
  - alias: "Außentemperatur an Wetterstation Kanal 2"
    triggers:
      - trigger: state
        entity_id: sensor.aussen_temperatur
      - trigger: time_pattern
        minutes: "/5"
    actions:
      - action: mqtt.publish
        data:
          topic: "cmnd/wlan2mqtt/irrfbridge1/cmtsensor"
          payload: >
            {"Channel":2,"Temperature":{{ states('sensor.aussen_temperatur') | float(0) | round(1) }},
             "Humidity":{{ states('sensor.aussen_feuchte') | int(50) }},
             "Id":"5A","Battery":1,"Interval":60,"Protocol":"Nexus"}
```

Die Bridge sendet danach jede Minute selbst weiter. Die Automation aktualisiert nur die Werte.

## 8. openHAB

Voraussetzungen: das **MQTT Binding** und die Transformation **JSONPath** (für JS-Filter zusätzlich **JavaScript Scripting**).

### 8.1 Things (`things/sh4.things`)

```java
Bridge mqtt:broker:mosquitto "Mosquitto" [ host="192.168.0.200", port=1883 ] {

    Thing topic sh4bridge1 "SH4 Bridge 1" {
    Channels:
        // alle Sensor-Telegramme roh - die Zuordnung zu einzelnen Sensoren macht die Regel in 8.3
        Type string : rfsensor "RF Sensor roh"     [ stateTopic="wlan2mqtt/irrfbridge1/RfSensor" ]
        Type string : rfcode   "RF Code"           [ stateTopic="wlan2mqtt/irrfbridge1/RfCode/get" ]
        Type string : rfproto  "RF Protokoll roh"  [ stateTopic="wlan2mqtt/irrfbridge1/RfProtocol" ]

        // Senden
        Type string : cmtsend   "RF senden"         [ commandTopic="cmnd/wlan2mqtt/irrfbridge1/cmtsend" ]
        Type string : cmtkaku   "KaKu senden"       [ commandTopic="cmnd/wlan2mqtt/irrfbridge1/cmtkaku" ]
        Type string : cmtsensor "Virt. Sensor"      [ commandTopic="cmnd/wlan2mqtt/irrfbridge1/cmtsensor" ]
        Type string : irsend    "IR senden"         [ commandTopic="cmnd/wlan2mqtt/irrfbridge1/IRSend" ]

        // Funksteckdose als Schalter
        Type switch : stehlampe "Stehlampe" [
            commandTopic="cmnd/wlan2mqtt/irrfbridge1/cmtkaku",
            on="1A2B3C 1 on", off="1A2B3C 1 off" ]
    }
}
```

> Einzelne Sensoren werden **per Regel** herausgefiltert (8.3) und nicht mit einem JSONPath-Filterausdruck im Channel. Ein Filter wie `$.RfSensor[?(@.Id=='3D')]` liefert je nach openHAB-Version eine Liste statt eines Werts und erzeugt Warnungen, wenn ein fremder Sensor sendet.

### 8.3 Rules (`rules/sh4.rules`)

```java
// Klingel erkannt
rule "RF Klingel"
when
    Item RF_Code received update "DEE308"
then
    Klingel.postUpdate(ON)
    createTimer(now.plusSeconds(5), [ | Klingel.postUpdate(OFF) ])
end

// Klingel per Funk auslösen (z. B. über einen Schalter in der UI)
rule "Klingel senden"
when
    Item Klingel received command ON
then
    RF_Senden.sendCommand("DEE308 20000 450 1450 20")
end

// Sensor-Telegramme den Items zuordnen (Protocol + Id)
rule "RF Sensor auswerten"
when
    Item RF_Sensor_Roh received update
then
    val json = RF_Sensor_Roh.state.toString
    val id = transform("JSONPATH", "$.RfSensor.Id", json)
    val proto = transform("JSONPATH", "$.RfSensor.Protocol", json)
    if (proto == "Nexus" && id == "3D") {
        WZ_Temp.postUpdate(transform("JSONPATH", "$.RfSensor.Temperature", json) + " °C")
        WZ_Feuchte.postUpdate(transform("JSONPATH", "$.RfSensor.Humidity", json) + " %")
    }
    // weitere Sensoren: weitere if-Zweige mit Protocol/Id
end

// Außentemperatur jede Minute an die Funk-Wetterstation (Kanal 2)
rule "Virtueller Sensor"
when
    Time cron "0 * * ? * *"
then
    if (Aussen_Temp.state instanceof QuantityType) {
        val t = (Aussen_Temp.state as QuantityType<Number>).doubleValue
        RF_VirtSensor.sendCommand(String::format(java.util.Locale.ROOT,
            "{\"Channel\":2,\"Temperature\":%.1f,\"Id\":\"5A\",\"Interval\":60,\"Protocol\":\"Nexus\"}", t))
    }
end
```

## 9. IR (Infrarot) auf dem SH4

Der SH4 hat zusätzlich einen IR-Sender (P7) und einen IR-Empfänger (P8). Dafür ist der OBK-Treiber `IR` zuständig.

```text
startDriver IR
IRSend NEC-1-1A-0           # Protokoll-Adresse-Befehl-Wiederholungen
IRSend Samsung-7-2-0
IRSend Sony-1-15-0
```

Empfangene Codes stehen im Log (`IR_NEC 0x1 0x1A 0 (32 bits)`). Per MQTT nach `<topic>/ir/get` gehen sie, wenn das OBK-Flag 14 („IR publish received“) gesetzt ist (*Config → General/Flags*).

### IR-Empfänger abschalten

**Ein IR-Empfänger, der Fremdlicht abbekommt, belegt fast die ganze CPU.** Ursachen können LED- oder Energiesparlampen, Fernseher, IR-Bewegungsmelder oder Kameras mit IR-Licht sein. Das Gerät wird dann träge, HTTP, MQTT und OTA scheitern, und der Heap fällt bis zum Neustart. Erkennbar ist das an `idle` unter ~10 000/s im Log, das sich nach `stopDriver IR` normalisiert.

Abhilfe, wenn der Standort nicht geändert werden kann:

```text
IREnable RX 0       # IR-Empfänger aus, Senden geht weiter (in autoexec.bat nach startDriver IR)
IREnable RX 1       # wieder ein
```

## 10. Grenzen und bekannte Probleme

- **Nur OOK/ASK.** FSK-Sensoren werden nicht empfangen. Das betrifft viele 868-MHz-Geräte, Bresser 5in1/6in1/7in1 und LaCrosse IT+.
- **Senden sehr kurzer Pulse:** TX141TH (208 µs) und Bresser3CH (250 µs) lassen sich mit `cmtsensor` nicht zuverlässig senden. Der Sender gibt Zeiten im 50-µs-Raster aus. Der **Empfang** dieser Protokolle funktioniert.
- **Somfy RTS** sendet auf 433,42 MHz statt 433,92 MHz und wird deshalb nur auf kurze Entfernung empfangen. Mit `cmtfreq` lässt sich die Frequenz verschieben, das ist aber nicht getestet. Andere Geräte würden dann schlechter empfangen.
- **Gleichzeitige Telegramme:** Kommen zwei längere Telegramme sehr dicht hintereinander, kann das zweite verloren gehen (`verworfen(belegt)` in `cmtproto`). Kurze Pakete puffert der Treiber zwischen.
- **Speicher:** Im Ruhezustand sind ~47–49 KB Heap frei. Dauerhaft offene Web-App-Tabs oder ein gestörter IR-Empfänger können das Gerät unter die 25-KB-Neustartgrenze drücken.
- **Doppelte Topics:** Sensor-Topics kommen mit und ohne `/get`. Auf eines davon festlegen.
